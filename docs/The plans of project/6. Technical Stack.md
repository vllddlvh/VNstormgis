### 2.1. Backend Core: Java 21 LTS & Spring Boot 3.3.x

**Decision:**
Sử dụng **Java 21 LTS** kết hợp với **Spring Boot 3.3.x** làm nền tảng phát triển duy nhất cho toàn bộ hệ thống xử lý Backend, Ingestion Engine, và REST API.

**Problem solved:**
Hệ thống đòi hỏi một nền tảng xử lý backend có khả năng:

1. Xử lý dữ liệu không gian phức tạp (Spatial Data Types) và giao tiếp mượt mà với PostgreSQL/PostGIS.
2. Thực hiện các tác vụ I/O định kỳ gọi API bên ngoài (OpenWeatherMap, GDACS, Gemini API) một cách đồng thời mà không nghẽn luồng.
3. Cung cấp kiến trúc module hóa chặt chẽ (Modular Monolith) để một đội ngũ nhỏ có thể bảo trì lâu dài, tránh tình trạng "Big Ball of Mud".
4. Kiểm soát lỗi chặt chẽ, type-safe ở mức biên dịch (compile-time safety).

**Why this technology:**

- **Virtual Threads (Project Loom) trong Java 21:** Cho phép xử lý hàng nghìn tác vụ I/O blocking (gọi HTTP WebClient sang OWM, GDACS, Gemini API) với chi phí tài nguyên phần cứng cực kỳ thấp, loại bỏ sự phức tạp của Reactive Programming (WebFlux) mà vẫn đạt hiệu năng tương đương.
- **Hệ sinh thái GIS vô địch:** Thư viện **JTS (Java Topology Suite)** và **Hibernate Spatial** là chuẩn mực cao cấp nhất để ánh xạ các đối tượng hình học (Point, Polygon, LineString) từ PostGIS lên các Java Object một cách tự nhiên.
- **Độ ổn định doanh nghiệp:** Spring Boot 3.3 mang lại bộ công cụ quản lý cấu hình (Profiles), Dependency Injection, Spring Security, Task Scheduling, và Connection Pooling (HikariCP) tốt nhất thế giới phần mềm, giúp team phát triển tập trung 100% vào logic nghiệp vụ thời tiết.

**Alternatives considered:**

1. **Go (Golang):** Rất nhẹ, khởi động nhanh, xử lý concurrency tốt bằng Goroutines.
2. **Python (FastAPI):** Lập trình nhanh, rất mạnh về thư viện khoa học dữ liệu và tích hợp AI.
3. **Node.js (NestJS / Express):** Phổ biến, chia sẻ chung ngôn ngữ JavaScript/TypeScript với Frontend.

**Why alternatives were rejected:**

- _Go bị loại bỏ vì:_ Thiếu một ORM/Spatial framework hoàn thiện như Hibernate Spatial/JTS. Việc ánh xạ kiểu hình học PostGIS, quản lý migration và validation trong Go đòi hỏi viết nhiều code boilerplate thủ công. Hệ sinh thái kiểm thử tích hợp (Testcontainers) của Go chưa trực quan bằng Java.
- _Python (FastAPI) bị loại bỏ vì:_ Hiệu năng CPU-bound và quản lý đa luồng (GIL) kém hơn Java. Khi cần tính toán phân tích dữ liệu không gian hoặc xử lý tác vụ quét định kỳ nền, Python tiêu tốn nhiều RAM và khó duy trì kiến trúc Clean Architecture ở quy mô lớn. Hệ thống type hint của Python chỉ mang tính gợi ý, dễ phát sinh lỗi runtime.
- _Node.js bị loại bỏ vì:_ Mô hình Single-Threaded Event Loop dễ bị nghẽn nếu có tác vụ tính toán hình học không gian phức tạp (Spatial Math). Thư viện TypeORM hay Prisma hỗ trợ PostGIS ở mức cơ bản, thiếu các hàm không gian chuyên sâu.

**Trade-offs:**

- _Ưu điểm:_ Độ tin cậy tuyệt đối, type-safety mạnh mẽ, hỗ trợ PostGIS hạng nhất, Virtual Threads giải quyết triệt để I/O blocking, công cụ kiểm thử tự động phong phú.
- _Nhược điểm:_ Thời gian khởi động (startup time) chậm hơn Go (~3-5 giây vs ~50ms), tiêu thụ RAM cơ sở cao hơn Go (khoảng 250MB - 350MB heap cho Spring Boot runtime).

**Impact:**

- _Development:_ Tốc độ viết code nhanh nhờ thư viện có sẵn phong phú, bắt lỗi ngay từ lúc biên dịch.
- _Performance:_ Đáp ứng < 50ms cho các truy vấn dữ liệu thời tiết và < 15ms cho các truy vấn GeoJSON trắc địa.
- _Scalability:_ Sẵn sàng scale ngang qua Docker container; dễ dàng bóc tách thành Microservices khi cần.
- _Reliability:_ Rất cao; hệ thống gõ kiểu tĩnh giảm 90% lỗi NullPointerException (nhờ Java Record & `@NonNull`).
- _Security:_ Được bảo vệ bởi Spring Security liên tục cập nhật bản vá bảo mật.
- _Maintainability:_ Xuất sắc nhờ kiến trúc Package-by-Feature và Clean Layering.
- _Cost:_ Cần máy chủ có tối thiểu 1GB - 2GB RAM (chi phí VPS khoảng $5 - $10/tháng, hoàn toàn nằm trong ngân sách).
- _Team learning curve:_ Rất thấp đối với backend developer đã có nền tảng hướng đối tượng (OOP).

### 2.2. Spatial Database: PostgreSQL 16 LTS & PostGIS 3.4

**Decision:**
Sử dụng **PostgreSQL 16** tích hợp phần mở rộng không gian **PostGIS 3.4** làm kho lưu trữ dữ liệu duy nhất cho toàn bộ hệ thống (dữ liệu thuộc tính, chuỗi thời gian khí tượng, tọa độ trạm, hình học bão, cấu hình ngưỡng và lịch sử hội thoại).

```
┌────────────────────────────────────────────────────────┐
│             POSTGRESQL 16 + POSTGIS 3.4                │
├──────────────────────────┬─────────────────────────────┤
│    DỮ LIỆU THUỘC TÍNH    │      DỮ LIỆU KHÔNG GIAN     │
│ - weather_records        │ - locations.geom (Point)    │
│ - alert_thresholds       │ - locations.boundary (Poly) │
│ - alerts, chat_messages  │ - storms.geom_current(Point)│
│ - data_sync_logs         │ - storm_tracks.geom / poly  │
│ [Chỉ mục B-Tree kép]     │ [Chỉ mục không gian GiST]   │
└──────────────────────────┴─────────────────────────────┘
```

**Problem solved:**
Hệ thống cần lưu trữ cả dữ liệu quan hệ (thời tiết chuỗi thời gian, tài khoản, cấu hình) lẫn dữ liệu hình học không gian (WGS84 Point, Polygon, LineString). Đặc biệt, hệ thống phải thực hiện các phép toán trắc địa phức tạp:

- Tính khoảng cách thực tế trên mặt cong Trái Đất giữa tâm bão và trạm quan sát (`ST_DistanceSphere`).
- Kiểm tra trạm hoặc điểm người dùng có nằm trong vùng gió bão nguy hiểm hay không (`ST_Intersects`, `ST_Contains`).
- Lọc các điểm cảnh báo nằm trong khung nhìn bản đồ của Leaflet (`Bounding Box`).

**Why this technology:**

- **PostGIS là chuẩn mực công nghiệp số 1:** Không có hệ quản trị CSDL nào trên thế giới hỗ trợ địa không gian vượt qua PostGIS về tính năng, độ chính xác toán học và hiệu năng chỉ mục.
- **Chỉ mục GiST (Generalized Search Tree):** Giúp tìm kiếm không gian (Spatial Search) đạt độ phức tạp $O(\log N)$, trả về kết quả trong vài mili-giây ngay cả khi tập dữ liệu mở rộng.
- **Chuẩn WGS84 (EPSG:4326):** Khớp 100% với chuẩn định dạng đầu ra GeoJSON RFC 7946 của bản đồ Leaflet.
- **Hỗ trợ JSONB:** Cho phép lưu trữ payload gốc của OpenWeatherMap và GDACS để audit hoặc mở rộng thuộc tính mà không cần sửa đổi cấu trúc bảng (Schema evolution).

**Alternatives considered:**

1. **MySQL 8.0 (Spatial Extensions):** CSDL quan hệ phổ biến có hỗ trợ tính năng GIS cơ bản.
2. **MongoDB (GeoSpatial Queries):** CSDL NoSQL hướng tài liệu hỗ trợ 2dsphere index.
3. **SQLite + SpatiaLite:** CSDL nhúng cực nhẹ.

**Why alternatives were rejected:**

- _MySQL 8.0 bị loại bỏ vì:_ Các hàm không gian của MySQL chỉ hỗ trợ tập con đơn giản; nhiều hàm tính toán trắc địa trên hình cầu (Ellipsoidal distance) hoạt động kém chính xác và hiệu năng chỉ mục R-Tree thấp hơn GiST của PostGIS.
- _MongoDB bị loại bỏ vì:_ Dữ liệu của hệ thống có quan hệ thực thể chặt chẽ (1 Trạm có N bản ghi thời tiết, 1 Bão có N điểm quỹ đạo, 1 Cảnh báo liên kết 1 Ngưỡng và 1 Trạm). MongoDB không đảm bảo tính toàn vẹn quan hệ (Foreign Key constraints) và các phép toán không gian phức tạp (ST_Buffer, ST_DistanceSphere) bị giới hạn nặng nề.
- _SpatiaLite bị loại bỏ vì:_ Không phù hợp cho ứng dụng web đa luồng ghi đồng thời (concurrency write lock); không hỗ trợ connection pooling và client-server model tiêu chuẩn.

**Trade-offs:**

- _Ưu điểm:_ Độ chính xác tuyệt đối, hỗ trợ đầy đủ các chuẩn OGC (Open Geospatial Consortium), cộng đồng khổng lồ, hiệu năng truy vấn cao.
- _Nhược điểm:_ Đòi hỏi kiến thức chuyên môn về kiểu dữ liệu địa lý (SRID, Projection, Geometry vs Geography) và cấu hình tối ưu bộ nhớ PostgreSQL (`shared_buffers`, `work_mem`).

**Impact:**

- _Development:_ Rút ngắn mã nguồn tầng ứng dụng; logic tính khoảng cách bão được giải quyết bằng 1 hàm SQL duy nhất (`ST_DistanceSphere`).
- _Performance:_ Truy vấn tìm trạm gần nhất và trạm vượt ngưỡng hoàn tất dưới 10ms.
- _Scalability:_ Xử lý mượt mà hàng triệu bản ghi `weather_records` với cơ chế Partitioning theo tháng khi dữ liệu tăng trưởng.
- _Reliability:_ Đạt chuẩn ACID đầy đủ, chống mất mát dữ liệu khi mất điện đột ngột nhờ WAL (Write-Ahead Logging).
- _Cost:_ Hoàn toàn miễn phí bản quyền (Open Source).

### 2.3. Frontend & WebGIS: React 18 & Leaflet

**Decision:**
Xây dựng Single Page Application (SPA) bằng **React 18** (kết hợp **TypeScript**) và thư viện bản đồ số **Leaflet** (thông qua wrapper `react-leaflet`).

**Problem solved:**
Giao diện người dùng phải hiển thị mượt mà bản đồ số toàn quốc với nhiều lớp thông tin động (lớp lượng mưa dạng điểm vòng tròn, lớp trường gió dạng vector mũi tên, lớp bão dạng biểu tượng xoáy kèm đường quỹ đạo) song song với một Panel danh sách cảnh báo và một Khung chat AI, tất cả tích hợp trên một màn hình duy nhất mà không giật lag.

**Why this technology:**

- **Leaflet cực kỳ nhẹ và nhanh:** Kích thước thư viện chỉ khoảng ~40KB (so với OpenLayers ~150KB hoặc Mapbox GL JS > 500KB). Leaflet tối ưu hóa xuất sắc việc vẽ các vector layer trên Canvas/SVG.
- **Tích hợp bản địa chuẩn GeoJSON:** Leaflet hỗ trợ nạp trực tiếp dữ liệu GeoJSON RFC 7946 từ Backend qua hàm `L.geoJSON(data)`, tự động ánh xạ thuộc tính thành Popup và Marker.
- **React 18 Component Lifecycle:** Cho phép phân chia giao diện thành các thành phần độc lập (`MapContainer`, `AlertList`, `ChatDrawer`), sử dụng React State để điều khiển việc bật/tắt lớp bản đồ tức thì mà không cần nạp lại trang.
- **TypeScript:** Đảm bảo 100% type-safety giữa định dạng GeoJSON Backend trả về và các handler sự kiện trên giao diện.

**Alternatives considered:**

1. **Mapbox GL JS:** Thư viện bản đồ vector cực đẹp, hỗ trợ 3D mượt mà.
2. **OpenLayers:** Thư viện WebGIS chuyên nghiệp, hỗ trợ đầy đủ mọi hệ quy chiếu và chuẩn GIS (WMS, WFS, WMTS).
3. **Vue.js:** Framework giao diện nhẹ, dễ học.

**Why alternatives were rejected:**

- _Mapbox GL JS bị loại bỏ vì:_ Ràng buộc giấy phép thương mại (phải có Access Token trả phí sau hạn mức), yêu cầu cấu hình Vector Tile Server phức tạp. Quy mô dữ liệu MVP (63 trạm đo) hoàn toàn không cần đến năng lực render hàng triệu vector tiles của Mapbox GL.
- _OpenLayers bị loại bỏ vì:_ Dung lượng thư viện quá nặng, cấu trúc API phức tạp, tài liệu khó tiếp cận, thời gian phát triển giao diện kéo dài không cần thiết cho một ứng dụng chỉ cần các tính năng bản đồ cơ bản.
- _Vue.js bị loại bỏ vì:_ Hệ sinh thái wrapper cho Leaflet (`vue-leaflet`) ít trưởng thành và ít cộng đồng hỗ trợ hơn `react-leaflet`.

**Trade-offs:**

- _Ưu điểm:_ Dung lượng tải trang web cực nhẹ, tốc độ hiển thị bản đồ gần như tức thì trên cả trình duyệt di động, tích hợp hoàn hảo với GeoJSON.
- _Nhược điểm:_ Leaflet hiển thị dạng bản đồ phẳng 2D, không hỗ trợ hiệu ứng xoay nghiêng 3D chuyên sâu như Mapbox GL (tuy nhiên SRS và BRD hoàn toàn không yêu cầu tính năng 3D).

**Impact:**

- _Development:_ Phát triển nhanh chóng, dễ bảo trì, dễ viết test giao diện.
- _Performance:_ Thời gian tải trang ban đầu (First Contentful Paint) < 1.5 giây; tương tác zoom/pan bản đồ đạt 60 FPS.
- _Maintainability:_ Tách biệt ranh giới rõ ràng giữa dữ liệu bản đồ và giao diện chat.
- _Cost:_ Không tốn chi phí bản quyền thư viện bản đồ; sử dụng mảnh bản đồ nền miễn phí từ OpenStreetMap hoặc CartoDB.

### 2.4. AI Reasoning: Google Gemini API (Gemini 1.5 Flash)

**Decision:**
Lựa chọn **Google Gemini API** (phiên bản mô hình **Gemini 1.5 Flash**) làm engine suy luận ngôn ngữ tự nhiên duy nhất cho cả hai chế độ: **Proactive AI Agent** (sinh cảnh báo tự động) và **Passive AI Agent** (hỏi đáp đối thoại có Grounding).

**Problem solved:**

1. **Chủ động:** Chuyển đổi các chỉ số khí tượng vượt ngưỡng khô khan thành bản tin cảnh báo dễ hiểu, phân tích ngữ nghĩa nguyên nhân nguy hiểm và khuyến nghị an toàn bằng tiếng Việt tự nhiên.
2. **Bị động:** Trả lời các câu hỏi tự nhiên của người dân dựa trên 100% dữ liệu thực tế trích xuất từ cơ sở dữ liệu (Grounding Rule), loại bỏ ảo giác (hallucination).

**Why this technology:**

- **Khả năng xử lý tiếng Việt vượt trội:** Mô hình Gemini được huấn luyện sâu trên tập dữ liệu đa ngôn ngữ, sinh văn bản tiếng Việt cực kỳ tự nhiên, hành văn chuẩn mực theo văn phong cảnh báo khí tượng thủy văn.
- **Chi phí tối ưu & Tốc độ siêu tốc (Gemini 1.5 Flash):** Thời gian sinh văn bản (Time to First Token) cực ngắn (< 1 giây), chi phí trên 1 triệu token cực kỳ cạnh tranh so với GPT-4o, phù hợp với ngân sách dự án cộng đồng.
- **System Instructions & Strict Grounding:** Hỗ trợ cấu hình chỉ thị hệ thống nghiêm ngặt, cho phép ép mô hình tuân thủ quy tắc: _"Chỉ sử dụng dữ kiện trong khối [FACTUAL_DATA], nghiêm cấm tự suy diễn số liệu"_.

**Alternatives considered:**

1. **OpenAI API (GPT-4o-mini / GPT-4o):** Dịch vụ LLM thương mại hàng đầu thế giới.
2. **Self-hosted Open Source LLM (Llama 3 / PhoGPT trên vLLM):** Tự host mô hình mã nguồn mở trên máy chủ riêng trang bị GPU.

**Why alternatives were rejected:**

- _OpenAI GPT-4o bị loại bỏ vì:_ Chi phí cuộc gọi API cao hơn; độ trễ mạng từ Việt Nam tới máy chủ OpenAI thỉnh thoảng biến động; thủ tục xuất hóa đơn và thanh toán cho dự án tại Việt Nam phức tạp hơn hạ tầng Google Cloud / AI Studio.
- _Self-hosted LLM (Llama 3 / PhoGPT) bị loại bỏ vì:_ Đòi hỏi máy chủ thuê GPU (NVIDIA A10G/T4) với chi phí tối thiểu $200 - $500/tháng, vượt xa ngân sách dự án MVP. Đồng thời làm tăng độ phức tạp vận hành hạ tầng lên gấp 10 lần.

**Trade-offs:**

- _Ưu điểm:_ Không mất chi phí hạ tầng máy chủ GPU, thời gian tích hợp cực nhanh qua REST WebClient, văn phong tiếng Việt rất tốt, chi phí theo lượt gọi rẻ.
- _Nhược điểm:_ Phụ thuộc vào tính khả dụng của bên thứ ba (Google Cloud). Đánh đổi này được hệ thống giảm thiểu bằng giải pháp kiến trúc **Deterministic Fallback Template (`SR-AGT-003`)** — nếu Gemini timeout hoặc lỗi, hệ thống tự động điền số liệu vào mẫu câu chuẩn định sẵn mà không làm trễ cảnh báo.

**Impact:**

- _Development:_ Tích hợp chỉ mất 2-3 ngày thông qua REST Client; không cần kỹ sư MLOps duy trì cụm máy chủ AI.
- _Cost:_ Miễn phí trong hạn mức Google AI Studio tier ban đầu, chi phí mở rộng chỉ từ $2 - $5/tháng cho lưu lượng vài nghìn lượt chat.
- _Reliability:_ Được bảo vệ 100% nhờ cơ chế Fallback và Guardrail Regex đối soát số liệu.

## 4. Backend Technology Decision

### 4.1. Phân Tích Chuyên Sâu: Java vs. Go vs. Các Lựa Chọn Khác

Một trong những quyết định kỹ thuật nền tảng là lựa chọn ngôn ngữ và nền tảng runtime cho Backend. Dưới đây là bảng phân tích toàn diện dựa trên 9 tiêu chí kỹ thuật:

| Tiêu Chí Kỹ Thuật                | Java (Java 21 LTS + Spring Boot 3)                                                                                          | Go (Golang 1.22+)                                                                                          | Python (FastAPI / Django)                                                                      | Node.js (NestJS / TypeScript)                                                                         |
| :------------------------------- | :-------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------- |
| **1. Spatial & GIS Ecosystem**   | ⭐⭐⭐⭐⭐ **Vô địch:** JTS (Java Topology Suite), GeoTools, Hibernate Spatial là chuẩn mực toàn cầu.                       | ⭐⭐⭐ **Trung bình:** Thư viện GIS hạn chế (`paulmach/orb`), thiếu ORM spatial chuẩn hóa.                 | ⭐⭐⭐⭐ **Khá:** GeoDjango mạnh, Shapely tốt nhưng tích hợp async còn phân mảnh.              | ⭐⭐⭐ **Trung bình:** Phụ thuộc Turf.js hoặc viết raw SQL cho PostGIS.                               |

**Kết luận kỹ thuật:**

- Mặc dù **Go** có ưu thế vượt trội về kích thước bộ nhớ và tốc độ khởi động, nhưng Go thiếu hệ sinh thái xử lý địa không gian (Spatial GIS ORM) mạnh mẽ như Hibernate Spatial / JTS. Việc lựa chọn Go sẽ buộc đội ngũ phát triển phải tự viết hàng trăm dòng code thủ công để parse hình học GeoJSON, ánh xạ WGS84 và xử lý giao dịch.
- **Java 21 kết hợp Spring Boot 3.3** là giải pháp cân bằng hoàn hảo nhất giữa: Khả năng tính toán địa không gian mạnh mẽ, khả năng xử lý concurrency xuất sắc nhờ Virtual Threads, kiểm thử tự động đỉnh cao với Testcontainers, và tính ổn định lâu dài của mã nguồn.

### 5.2. Các Quyết Định Kỹ Thuật Chi Tiết Cho Database

1. **Schema Strategy (Chiến lược Lược đồ):**
   - Áp dụng lược đồ quan hệ chuẩn hóa (3NF) gồm 10 bảng như đã đặc tả trong [1. ERD.md](file:///Users/dllv/Documents/GitHub/VNstormgis/docs/The%20plans%20of%20project/1.%20ERD.md).
   - Khóa chính của các thực thể quan trọng (`locations`, `alerts`, `chat_sessions`, `chat_messages`) sử dụng chuẩn **UUID v4** (`DEFAULT gen_random_uuid()`) để bảo mật, chống đoán ID tuần tự.
   - Các bảng chuỗi thời gian nạp định kỳ (`weather_records`, `storm_tracks`, `data_sync_logs`) sử dụng **BIGSERIAL** tự tăng để tối ưu hóa hiệu năng ghi và dung lượng chỉ mục.
   - Dữ liệu hình học không gian được lưu trữ dưới dạng kiểu nhị phân không gian chuẩn: `GEOMETRY(Point, 4326)` và `GEOMETRY(Polygon, 4326)` với hệ quy chiếu chuẩn thế giới WGS84.

2. **Indexing Strategy (Chiến lược Lập chỉ mục):**
   - **Chỉ mục không gian GiST (Spatial Index):**
     - `idx_locations_geom`: Tăng tốc truy vấn tìm trạm gần vị trí người dùng (`ST_DWithin`).
     - `idx_storms_geom_current`: Tăng tốc tìm bão active và tính khoảng cách tới đất liền.
     - `idx_storm_tracks_geom` & `idx_storm_tracks_impact_polygon`: Tăng tốc vẽ quỹ đạo và kiểm tra vùng nguy hiểm.
     - `idx_alerts_affected_geom`: Hỗ trợ lọc các cảnh báo hiển thị trong Bounding Box của Leaflet.
   - **Chỉ mục B-Tree phức hợp (Composite Indexes):**
     - `weather_records(location_id, recorded_at DESC)`: Đảm bảo truy vấn lấy bản ghi thời tiết mới nhất của mỗi trạm đạt độ phức tạp $O(\log N)$ với thời gian thực thi < 2ms.
     - `storm_tracks(storm_id, forecast_time ASC)`: Lấy quỹ đạo bão theo thứ tự thời gian.
     - `alerts(status, triggered_at DESC)`: Lọc cảnh báo khẩn cấp đang kích hoạt (`status = 'active'`).
     - `chat_messages(session_id, created_at ASC)`: Tải lại dòng thời gian lịch sử hội thoại tức thì.

3. **Transaction Model & Consistency (Mô hình Giao dịch & Nhất quán):**
   - Tuân thủ mô hình **ACID** nghiêm ngặt.
   - Mức độ cô lập mặc định: **Read Committed** (cân bằng hoàn hảo giữa tính nhất quán và hiệu năng đồng thời, không gây hiện tượng Dirty Read).
   - Các thao tác nạp dữ liệu định kỳ (ghi chuỗi trạm) và phát cảnh báo AI được bọc trong `@Transactional` của Spring để đảm bảo tính nguyên tử (Atomic): Nếu có lỗi xảy ra giữa chừng, toàn bộ transaction được rollback, không để lại dữ liệu rác.

4. **Connection Pooling: HikariCP**
   - _Quyết định:_ Sử dụng **HikariCP** (mặc định của Spring Boot).
   - _Cấu hình sản xuất:_
     - `maximum-pool-size`: 15 connections (hoàn toàn dư sức đáp ứng hàng trăm request/giây cho một single host).
     - `minimum-idle`: 5 connections.
     - `connection-timeout`: 30,000 ms.
     - `idle-timeout`: 600,000 ms.
     - `max-lifetime`: 1,800,000 ms.

5. **Migration & Versioning: Flyway**
   - _Quyết định:_ Toàn bộ DDL được quản lý qua Flyway trong thư mục `resources/db/migration/`.
   - _Quy tắc:_ Tuyệt đối không dùng `ddl-auto: update` của Hibernate trong môi trường Production. Mọi thay đổi schema đều phải qua script SQL được đánh số phiên bản (`V1__...`, `V2__...`).

6. **Chiến lược Sao lưu & Phục hồi (Backup & Recovery):**
   - _Daily Dump:_ Sử dụng lệnh `pg_dump` nén nhị phân định kỳ hàng đêm vào lúc 02:00 sáng qua cron script trên host:
     ```bash
     pg_dump -Fc -U gis_user -d weather_gis_db > /backups/weather_gis_$(date +%Y%m%d).dump
     ```
   - _Retention:_ Giữ 7 bản sao lưu gần nhất trên đĩa cứng; tự động xóa các bản cũ hơn để tiết kiệm dung lượng.

### 6.1. Cache (Redis 7)

- **Có thực sự cần không?** $\rightarrow$ **CỰC KỲ CẦN THIẾT**.
- **Quyết định:** Sử dụng **Redis 7.2.x (Alpine)** thông qua thư viện `spring-boot-starter-data-redis` với driver **Lettuce** (Non-blocking I/O).
- **Dùng cho các use case cụ thể nào?**
  1. **Danh mục 63 trạm quan trắc (`weathergis:locations`):** Dữ liệu tĩnh, TTL = 24 giờ. Giảm thiểu các truy vấn lặp lại danh sách trạm.
  2. **Bảng quy chuẩn ngưỡng cảnh báo (`weathergis:thresholds`):** Đọc liên tục bởi worker quét ngưỡng, TTL = 1 giờ. Khi Quản trị viên cập nhật ngưỡng qua API, hệ thống tự động xóa cache bằng `@CacheEvict(value = "thresholds", allEntries = true)`.
  3. **Dữ liệu thời tiết hiện tại GeoJSON (`weathergis:weather:current`):** Chuỗi FeatureCollection GeoJSON của 63 trạm được serialize sẵn, TTL = 15 phút (khớp chu kỳ đồng bộ OWM). Khi xảy ra thiên tai hoặc bão đổ bộ, hàng chục nghìn người dân truy cập WebGIS cùng lúc sẽ đọc trực tiếp từ Redis trong < 2ms, giảm tải 95% truy vấn xuống PostgreSQL/PostGIS và bảo vệ Connection Pool.
  4. **Danh sách bão và quỹ đạo bão (`weathergis:storms:active`):** Cache kết quả từ GDACS, TTL = 30 phút.
  5. **Quản lý Rate Limiting phân tán (`weathergis:ratelimit:{sessionId/ip}`):** Lưu trữ Token Bucket của thuật toán Bucket4j (10 requests/phút cho Chatbot). Giúp duy trì giới hạn tần suất chuẩn xác và giữ Backend Spring Boot hoàn toàn stateless khi scale nhiều container.
- **Khi nào request đi qua component này?**
  - Mọi request của Client hỏi danh sách trạm (`/locations`), thời tiết bản đồ (`/weather/current`), bão (`/storms`) hoặc gửi câu hỏi chatbox (`/chat/message`) đều đi qua Redis trước tiên (Cache-Aside Pattern & Rate Limit Filter).
- **Cấu hình kỹ thuật & Tối ưu hóa tài nguyên:**
  - _Driver kết nối:_ **Lettuce** kết hợp connection pool (Commons Pool 2), giao tiếp phi phong tỏa non-blocking.
  - _Định dạng Serialization:_ `StringRedisSerializer` cho Key (dễ đọc, dễ tra cứu trên `redis-cli`), `GenericJackson2JsonRedisSerializer` tích hợp `JavaTimeModule` cho Value (hỗ trợ chuyển đổi mượt mà các trường thời gian ISO 8601 và cấu trúc GeoJSON).
  - _Quản lý RAM an toàn:_ Cấu hình `maxmemory 128mb` kèm chính sách dọn dẹp `maxmemory-policy allkeys-lru` trong file `docker-compose.yml`. Đảm bảo Redis chỉ chiếm tối đa 128MB RAM, hoàn toàn vừa vặn với cấu hình VPS giá rẻ ($10 - $20/tháng).
- **Nếu Redis bị lỗi thì hệ thống xử lý thế nào (Resilience & Graceful Degradation)?**
  - Triển khai custom `CacheErrorHandler` trong Spring Boot. Nếu container Redis bị gián đoạn, sập hoặc timeout, Spring Boot tự động bắt exception, ghi log cảnh báo `WARN` và chuyển hướng truy vấn trực tiếp xuống PostgreSQL/PostGIS.
  - Nhờ cơ chế chỉ mục không gian GiST và B-Tree của PostgreSQL, hệ thống vẫn duy trì hoạt động bình thường mà không bao giờ trả lỗi HTTP 500 cho người dùng cuối. Khi Redis online trở lại, Lettuce sẽ tự động tái kết nối (`Auto-reconnect`) mà không cần restart Backend.

### 6.2. Message Broker (Kafka / RabbitMQ)

- **Có thực sự cần không?** $\rightarrow$ **KHÔNG CẦN**.
- **Decision: NOT USED (Kafka / RabbitMQ / SQS $\rightarrow$ Not used)**.
- **Lý do kỹ thuật (Why rejected):**
  1. **Bản chất luồng dữ liệu:** Hệ thống nạp dữ liệu khí tượng theo phương thức **Pull định kỳ (Batch Polling)** mỗi 15-30 phút từ OpenWeatherMap và GDACS. Hệ thống không tiếp nhận dòng dữ liệu stream hàng triệu sự kiện/giây từ hàng nghìn cảm biến IoT để cần đến khả năng log-partitioning của Kafka hay queuing của RabbitMQ.
  2. **Tác vụ nền nội bộ:** Spring Boot cung cấp sẵn **Spring TaskScheduler (`@Scheduled`)** và **ThreadPoolTaskExecutor** chạy in-process. Việc gửi sự kiện vi phạm ngưỡng từ Worker sang AI Agent được thực hiện qua **Spring ApplicationEventPublisher** cực kỳ nhẹ nhàng, đồng bộ hoặc bất đồng bộ tùy cấu hình, không tốn độ trễ mạng và không phát sinh chi phí duy trì cụm máy chủ broker.
  3. **Chi phí vận hành:** Kafka đòi hỏi tối thiểu 3 broker + Zookeeper/KRaft, tiêu thụ tối thiểu 2GB - 4GB RAM, vượt quá toàn bộ tài nguyên của một máy chủ MVP.
- **Kế hoạch mở rộng tương lai:** Chỉ cân nhắc tích hợp RabbitMQ khi hệ thống nâng cấp thêm tính năng tiếp nhận trực tiếp dữ liệu từ mạng lưới hàng nghìn trạm cảm biến IoT thời tiết tự động của cơ quan nhà nước.

- **Có thực sự cần không?** $\rightarrow$ **KHÔNG CẦN**.
- **Decision: NOT USED (AWS S3 / MinIO $\rightarrow$ Not used)**.

## 7. Cloud Technology Decision

### 7.1. Định Hướng Chiến Lược Triển Khai Cloud Cho MVP

Để đảm bảo hiệu quả chi phí tối đa cho dự án mang tính chất cộng đồng và nghiên cứu ứng dụng, hệ thống áp dụng chiến lược triển khai:

- **Giai đoạn MVP (Hiện tại):** Triển khai trên **01 Máy Chủ Ảo Độc Lập (Single VPS Host)** sử dụng **Docker Compose** (chạy trên Ubuntu 22.04 LTS). Có thể đặt trên **AWS Lightsail**, **DigitalOcean**, **Hetzner** hoặc nhà cung cấp VPS uy tín trong nước (Viettel Cloud, VNPT, FPT).
- **Giai đoạn Scale (Khi có bão lớn, lượng truy cập tăng vọt):** Sẵn sàng chuyển đổi kiến trúc sang các dịch vụ đám mây chuyên biệt của **Amazon Web Services (AWS)** mà không cần đập đi viết lại mã nguồn.

### 7.2. Phân Tích Các Dịch Vụ AWS (Khi Cần Triển Khai Trên AWS)

Nếu hệ thống được triển khai trên nền tảng **Amazon Web Services (AWS)**, các dịch vụ sau được lựa chọn và ánh xạ kỹ thuật:

```
┌────────────────────────────────────────────────────────┐
│                 AWS CLOUD ARCHITECTURE                 │
├────────────────────────────────────────────────────────┤
│ DNS & CDN:       Route 53                              │
│ Load Balancer:   AWS Application Load Balancer (ALB)   │
│ Compute:         AWS EC2 (t4g.small / t4g.medium)      │
│ Database:        AWS RDS for PostgreSQL (PostGIS)      │
│ Container Reg:   AWS ECR (Elastic Container Reg)       │
│ Secrets:         AWS Systems Manager Parameter Store   │
│ Observability:   AWS CloudWatch Logs & Metrics         │
└────────────────────────────────────────────────────────┘
```

#### 1. Compute

- **AWS Service:** **Amazon EC2 (Instance Type: `t4g.small` hoặc `t4g.medium` ARM-based Graviton2/3)**
- **Purpose:** Chạy Docker host chứa Nginx và Spring Boot Backend container.
- **Why this service:** Dòng vi xử lý ARM Graviton mang lại hiệu năng trên giá thành (Price/Performance) tốt hơn 20% so với x86 (Intel/AMD). Cấu hình 2 vCPU, 2GB - 4GB RAM hoàn toàn đủ gánh toàn bộ tải MVP với chi phí cực thấp (~$10 - $25/tháng).
- **Alternative:** AWS ECS Fargate hoặc AWS Lambda.
- **Cost consideration:** EC2 trả phí cố định hàng tháng (có thể dùng Savings Plans), rẻ hơn đáng kể so với việc chạy Fargate 24/7 cho các worker nạp định kỳ.

#### 2. Database

- **AWS Service:** **Amazon RDS for PostgreSQL (db.t4g.micro hoặc db.t4g.small)**
- **Purpose:** Lưu trữ CSDL PostgreSQL 16 và kích hoạt extension PostGIS.
- **Why this service:** RDS tự động hóa hoàn toàn việc sao lưu hàng ngày (Automated Backups), tự động cập nhật bản vá bảo mật, quản lý Multi-AZ khi cần dự phòng thảm họa, giải phóng đội ngũ kỹ sư khỏi công việc quản trị CSDL vật lý.
- **Alternative:** Tự cài PostgreSQL trên EC2.
- **Cost consideration:** RDS đắt hơn tự cài trên EC2 khoảng 1.5 lần (~$15 - $30/tháng), nhưng bù lại rủi ro mất dữ liệu gần như bằng 0.

#### 3. Networking & Security

- **AWS Service:** **Amazon VPC (Virtual Private Cloud) + Security Groups**
- **Purpose:** Phân vùng mạng và cô lập an toàn cơ sở dữ liệu.
- **Why this service:** Đặt RDS PostgreSQL trong Private Subnet (không có Public IP), chỉ cho phép EC2 Backend trong Public Subnet kết nối vào cổng 5432 thông qua Security Group. Chặn đứng 100% các cuộc tấn công rà quét cổng CSDL từ Internet.
- **Alternative:** Mở trực tiếp CSDL ra Internet với mật khẩu mạnh (Cực kỳ nguy hiểm, vi phạm tiêu chuẩn an ninh thông tin).
- **Cost consideration:** VPC và Security Groups hoàn toàn miễn phí.

#### 4. Load Balancing & SSL Termination

- **AWS Service:** **AWS Application Load Balancer (ALB)** (Tùy chọn khi scale)
- **Purpose:** Tiếp nhận lưu lượng HTTPS cổng 443, cấp phát chứng chỉ SSL miễn phí qua AWS Certificate Manager (ACM), phân phối tải tới các backend container.
- **Alternative:** Nginx tự cấu hình Certbot Let's Encrypt trên EC2.
- **Cost consideration:** Cho giai đoạn MVP ban đầu, sử dụng Nginx + Let's Encrypt trực tiếp trên EC2 để tiết kiệm chi phí ALB (~$16 - $20/tháng). Khi lượng người dùng tăng đột biến, mới kích hoạt ALB.

#### 5. Container Registry

- **AWS Service:** **Amazon ECR (Elastic Container Registry)**
- **Purpose:** Lưu trữ các Docker image đã build của Frontend và Backend.
- **Why this service:** Tích hợp bảo mật tự động quét lỗ hổng ảnh (Vulnerability Scanning) và phân quyền chặt chẽ qua IAM.
- **Alternative:** Docker Hub hoặc GitHub Packages.
- **Cost consideration:** Chi phí lưu trữ vài GB image chỉ khoảng < $1/tháng.

#### 6. Secrets Management

- **AWS Service:** **AWS Systems Manager Parameter Store (Standard)**
- **Purpose:** Lưu trữ các khóa API (`OWM_API_KEY`, `GEMINI_API_KEY`, `DB_PASSWORD`).
- **Why this service:** Loại Standard hoàn toàn **miễn phí**, bảo mật mã hóa bằng AWS KMS, tích hợp trực tiếp khi khởi động container trên EC2.
- **Alternative:** AWS Secrets Manager ($0.40/secret/tháng $\rightarrow$ Tốn kém không cần thiết).
- **Cost consideration:** Miễn phí 100%.

#### 7. Monitoring & Logging

- **AWS Service:** **Amazon CloudWatch**
- **Purpose:** Thu thập metric CPU/RAM của EC2, giám sát trạng thái RDS và cảnh báo khi máy chủ quá tải.
- **Alternative:** Tự dựng Prometheus + Grafana.
- **Cost consideration:** Nằm trọn vẹn trong AWS Free Tier.

### 8.2. Chi Tiết Các Thành Phần Hạ Tầng

1. **Docker Multi-Stage Build:**
   - **Backend Dockerfile:**
     - _Stage 1 (Builder):_ Sử dụng image `gradle:8.8-jdk21-alpine` (hoặc image JDK 21 kết hợp Gradle Wrapper `./gradlew bootJar`) để biên dịch mã nguồn và đóng gói file JAR. Tận dụng Docker layer caching cho cache dependencies để rút ngắn thời gian build.
     - _Stage 2 (Runtime):_ Sử dụng image siêu nhẹ `bellsoft/liberica-openjre-alpine:21`. Chạy ứng dụng dưới người dùng không có quyền root (`non-root user: appuser`) để tăng cường an ninh. Kích hoạt cờ Virtual Threads và tối ưu JVM memory:
       ```dockerfile
       ENTRYPOINT ["java", "-XX:+UseG1GC", "-XX:MaxRAMPercentage=75.0", "-jar", "app.jar"]
       ```
   - **Frontend Dockerfile:**
     - _Stage 1 (Builder):_ Sử dụng image `node:20-alpine` chạy `npm run build` để xuất mã tĩnh tối ưu.
     - _Stage 2 (Runtime):_ Sử dụng image `nginx:1.26-alpine`, copy gói build tĩnh vào thư mục `/usr/share/nginx/html`.

2. **Docker Compose Orchestration:**
   - Toàn bộ hệ thống Production được định nghĩa trong file `deployment/docker-compose.yml` gồm 4 containers chạy trên một mạng nội bộ ảo (`backend-network`):
     - `db`: Container PostGIS (PostgreSQL 16 + PostGIS 3.4) với volume bền vững `postgis_data`.
     - `redis`: Container Redis 7 Alpine (`weathergis-redis`) với cờ giới hạn `--maxmemory 128mb --maxmemory-policy allkeys-lru` và volume lưu tạm `redis_data`.
     - `backend`: Container Spring Boot, phụ thuộc `db` và `redis` kèm healthcheck.
     - `web`: Container Nginx, mở cổng 80 và 443 ra Internet, làm cổng vào duy nhất.

3. **Tại sao KHÔNG sử dụng Kubernetes (Why Kubernetes was rejected):**
   - _Decision: Kubernetes $\rightarrow$ NOT USED_.
   - _Lý do:_ Quy mô hệ thống hiện tại là một **Modular Monolith** gồm 1 backend process, 1 database instance, 1 redis cache instance và 1 web proxy tĩnh. Triển khai Kubernetes (K8s) sẽ đòi hỏi:
     - Tối thiểu 3 master nodes + 2 worker nodes (chi phí tăng gấp 5 - 10 lần).
     - Quản lý Ingress Controller, Helm Charts, PVC (Persistent Volume Claims), MetalLB/CSI driver cực kỳ phức tạp.
     - Đội ngũ vận hành phải có chứng chỉ CKA/CKS để xử lý sự cố.
     - Đây là biểu hiện kinh điển của **Over-engineering**. Docker Compose hoàn toàn đáp ứng 100% nhu cầu vận hành, phục hồi sau sự cố chỉ bằng 1 dòng lệnh.

4. **Tại sao KHÔNG sử dụng Terraform cho MVP:**
   - _Decision: Terraform / CloudFormation $\rightarrow$ NOT USED cho MVP_.
   - _Lý do:_ Hạ tầng MVP chỉ bao gồm 1 máy chủ ảo và các biến môi trường cấu hình. Việc thiết lập có thể thực hiện nhanh chóng qua một shell script chuẩn hóa (`scripts/setup_dev_env.sh`). Sẽ chỉ áp dụng Terraform khi mở rộng lên hạ tầng đa dịch vụ AWS (RDS, ALB, VPC, Multi-AZ).

5. **Chiến lược Kiểm tra Sức Khỏe (Health Check) & Tự Khởi Động Lại:**
   - Trong `docker-compose.yml`, mỗi dịch vụ đều được cấu hình healthcheck định kỳ:
     - `db`: `pg_isready -U gis_user -d weather_gis_db` (mỗi 10s).
     - `redis`: `redis-cli ping` (mỗi 10s).
     - `backend`: `curl -f http://localhost:8080/actuator/health` (mỗi 15s).
     - Thuộc tính `restart: unless-stopped` đảm bảo nếu container gặp sự cố crash hoặc máy chủ khởi động lại, toàn bộ stack tự động phục hồi mà không cần can thiệp thủ công.

6. **Chiến lược Rollback (Hoàn Lại Phiên Bản Cũ):**
   - Mỗi bản build CI/CD trên GitHub Actions đều gắn thẻ Docker Image theo Git Commit SHA (ví dụ: `weathergis-backend:sha-a1b2c3d`).
   - Nếu phiên bản mới gặp lỗi nghiêm trọng sau khi triển khai, người vận hành chỉ cần sửa lại biến môi trường `IMAGE_TAG` về SHA ổn định trước đó trong file `.env` và chạy:
     ```bash
     docker compose up -d
     ```
     Toàn bộ quá trình rollback hoàn tất trong vòng chưa đầy 30 giây.

## 10. Observability

Thiết kế hệ thống quan sát tập trung vào tính thực tế và hiệu quả, tránh triển khai các giải pháp quá cồng kềnh cho giai đoạn MVP:

```
┌────────────────────────────────────────────────────────┐
│                   OBSERVABILITY STACK                  │
├──────────────────────────┬─────────────────────────────┤
│         LOGGING          │           METRICS           │
│ SLF4J + Logback          │ Spring Boot Actuator        │
│ - Rolling File Appender  │ - /actuator/health          │
│ - Bảng data_sync_logs    │ - /actuator/metrics         │
└──────────────────────────┴─────────────────────────────┘
```

### 10.1. Logging

- **Technology:** **SLF4J** facade kết hợp **Logback** implementation.
- **Định dạng:** Chuẩn cấu trúc có dấu thời gian (ISO 8601), cấp độ log (`INFO`, `WARN`, `ERROR`), thread ID và tên class.
- **Cấu hình lưu trữ:**
  - _Console Appender:_ Phục vụ xem log trực tiếp qua lệnh `docker compose logs -f backend`.
  - _Rolling File Appender:_ Ghi vào thư mục `/app/logs/weathergis.log`. Thiết lập chính sách xoay vòng theo ngày (`TimeBasedRollingPolicy`), nén file `.gz` cho các ngày cũ, tự động xóa log sau 30 ngày hoặc khi tổng dung lượng vượt 2GB.
- **Database Audit Logging:** Bảng `data_sync_logs` lưu trữ chuyên biệt trạng thái của các worker nạp dữ liệu (`OPENWEATHERMAP`, `GDACS`, `AI_MONITOR`) phục vụ tra cứu qua endpoint quản trị `/api/v1/internal/sync-logs`.

### 10.2. Metrics & Health Check

- **Technology:** **Spring Boot Actuator** tích hợp sẵn.
- **Endpoints kích hoạt:**
  - `GET /actuator/health`: Trả về trạng thái tổng thể của hệ thống (`UP` hoặc `DOWN`), kiểm tra kết nối sống còn tới PostgreSQL/PostGIS, dung lượng ổ đĩa. Endpoint này được sử dụng làm Docker Healthcheck.
  - `GET /api/v1/health`: Endpoint công khai chuẩn hóa trả về phiên bản ứng dụng, trạng thái kết nối PostGIS, trạng thái sẵn sàng của Gemini API và thời điểm đồng bộ dữ liệu gần nhất ([API Docs Section 3.7.1](file:///Users/dllv/Documents/GitHub/VNstormgis/docs/The%20plans%20of%20project/2.%20API%20docs.md#L1060)).
  - `GET /actuator/metrics`: Cung cấp các chỉ số hiệu năng chuẩn Micrometer (JVM Memory, Thread Count, HikariCP Active Connections, HTTP Request Duration).

### 10.3. Monitoring & Alerting

- **Technology:** **Uptime Kuma** (hoặc CloudWatch / Better Uptime).
- **Mức độ cần thiết:** Thiết lập 1 monitor HTTP kiểm tra endpoint `https://api.weathergis.vn/api/v1/health` mỗi 60 giây. Nếu hệ thống trả về mã khác 200 hoặc timeout quá 10 giây $\rightarrow$ Tự động gửi cảnh báo khẩn cấp tới Telegram / Discord của nhóm kỹ sư trực ban.

### 10.4. Tracing

- **Decision: NOT USED (Jaeger / Zipkin / OpenTelemetry $\rightarrow$ Not used)**.
- **Lý do:** Hệ thống được thiết kế theo kiến trúc **Modular Monolith**. Mọi luồng xử lý từ Controller $\rightarrow$ Service $\rightarrow$ Repository đều diễn ra in-process trong cùng một JVM. Không có các cuộc gọi mạng phân tán giữa hàng chục microservices để cần đến Distributed Tracing. Việc đưa OpenTelemetry Collector và Jaeger vào lúc này sẽ làm lãng phí 200MB - 400MB RAM và tăng thêm độ phức tạp không đáng có.

### ADR-001: Lựa Chọn Phong Cách Kiến Trúc Modular Monolith

- **Status:** Accepted
- **Context:**
  Dự án cần một nền tảng vận hành ổn định phục vụ người dân theo dõi thời tiết, bão và cảnh báo. Các domain nghiệp vụ (Trạm, Thời tiết, Bão, Ngưỡng, Cảnh báo, Chat) có mối liên hệ dữ liệu chặt chẽ. Đội ngũ phát triển tinh gọn, ngân sách vận hành máy chủ ở mức cơ bản.
- **Decision:**
  Áp dụng phong cách kiến trúc **Modular Monolith** chạy trên một tiến trình Java duy nhất. Mã nguồn được tổ chức theo từng Domain Feature riêng biệt (`location`, `weather`, `storm`, `threshold`, `alert`, `chat`, `automation`), giao tiếp nội bộ qua Java Service Interface công khai và Spring Application Events.
- **Alternatives:**
  Microservices Architecture, Traditional Layered Monolith.
- **Consequences:**
  - _Tích cực:_ Đơn giản hóa tối đa quy trình CI/CD và deployment (chỉ 1 Docker container duy nhất); không có độ trễ mạng nội bộ; dễ dàng thực hiện giao dịch ACID xuyên suốt các bảng; dễ debug và kiểm thử tự động.
  - _Tiêu cực:_ Đòi hỏi tính kỷ luật cao của lập trình viên để không vi phạm quy tắc gọi chéo dữ liệu giữa các package.
- **Trade-offs:** Chấp nhận việc scale ứng dụng phải scale toàn bộ tiến trình thay vì scale lẻ từng service, hoàn toàn phù hợp với quy mô MVP.

### ADR-002: Lựa Chọn Java 21 LTS & Spring Boot 3 Cho Backend Core

- **Status:** Accepted
- **Context:**
  Hệ thống đòi hỏi năng lực xử lý dữ liệu địa không gian mạnh mẽ, concurrency non-blocking khi gọi nhiều external APIs đồng thời, và một hệ sinh thái kiểm thử tích hợp CSDL PostGIS chuẩn hóa.
- **Decision:**
  Sử dụng **Java 21 LTS** kết hợp **Spring Boot 3.3.x**, kích hoạt Virtual Threads (Project Loom) và thư viện Hibernate Spatial / JTS.
- **Alternatives:**
  Go (Golang + Gin), Python (FastAPI), Node.js (NestJS).
- **Consequences:**
  - _Tích cực:_ Hỗ trợ kiểu dữ liệu không gian PostGIS bản địa xuất sắc nhất thế giới; Virtual Threads giúp code tuần tự mà vẫn đạt hiệu năng I/O song song tương đương Go; hệ thống gõ kiểu tĩnh và kiểm thử Testcontainers loại bỏ 95% lỗi runtime.
  - _Tiêu cực:_ Tiêu thụ bộ nhớ RAM cao hơn Go (~300MB vs ~40MB), thời gian khởi động chậm hơn (~3s vs ~50ms).
- **Trade-offs:** Đánh đổi một phần RAM máy chủ để đổi lấy sự toàn diện của hệ sinh thái GIS và độ tin cậy của mã nguồn.

### ADR-003: Quản Lý Dữ Liệu Không Gian Bằng PostgreSQL 16 & PostGIS 3.4

- **Status:** Accepted
- **Context:**
  Hệ thống cần tính toán khoảng cách trắc địa thực tế giữa tâm bão và trạm quan trắc trên mặt cong Trái Đất, lưu trữ đa giác vùng ảnh hưởng và xuất bản dữ liệu chuẩn GeoJSON RFC 7946 cho Leaflet.
- **Decision:**
  Sử dụng **PostgreSQL 16 LTS** với phần mở rộng **PostGIS 3.4**, hệ quy chiếu không gian chuẩn WGS84 (EPSG:4326), kết hợp chỉ mục GiST Index.
- **Alternatives:**
  MySQL 8.0 Spatial, MongoDB GeoSpatial, SQLite + SpatiaLite.
- **Consequences:**
  - _Tích cực:_ Cung cấp độ chính xác toán học tuyệt đối qua hàm `ST_DistanceSphere` và `ST_Intersects`; hiệu năng tìm kiếm không gian đạt tốc độ $O(\log N)$; lưu trữ đồng thời dữ liệu quan hệ và JSONB audit.
  - _Tiêu cực:_ Yêu cầu lập trình viên hiểu biết về trắc địa và cú pháp hàm không gian SQL.
- **Trade-offs:** Cấu hình PostgreSQL đòi hỏi tinh chỉnh tham số bộ nhớ, bù lại hệ thống có một nền tảng CSDL không gian số 1 thế giới.

### ADR-004: Sử Dụng In-Process TaskScheduler Thay Vì Message Broker Ngoài Cho MVP

- **Status:** Accepted
- **Context:**
  Hệ thống cần nạp dữ liệu thời tiết và bão định kỳ (15-30 phút/lần) và quét ngưỡng rủi ro. Nhiều kiến trúc sư thường có xu hướng đưa Kafka hoặc RabbitMQ vào như một thói quen.
- **Decision:**
  Quyết định **KHÔNG sử dụng Message Broker ngoài** cho phiên bản MVP. Sử dụng giải pháp in-process: **Spring TaskScheduler (`@Scheduled`)** kết hợp **Spring ApplicationEventPublisher**.
- **Alternatives:**
  Apache Kafka, RabbitMQ, AWS SQS.
- **Consequences:**
  - _Tích cực:_ Tiết kiệm 100% chi phí và tài nguyên duy trì cụm máy chủ broker riêng; loại bỏ hoàn toàn các lỗi mất kết nối broker hay phân tán transaction; triển khai gọn gàng trong 1 container.
  - _Tiêu cực:_ Tác vụ chạy nền chia sẻ CPU/RAM với tiến trình phục vụ REST API (đã được cách ly bằng ThreadPool riêng).
- **Trade-offs:** Chấp nhận không có cơ chế event streaming phân tán vì bản chất dữ liệu là nạp định kỳ dạng batch.

---

### ADR-005: Sử Dụng Redis 7 Làm Distributed Cache Tập Trung & Quản Lý Rate Limit

- **Status:** Accepted
- **Context:**
  Hệ thống WebGIS cần phục vụ liên tục dữ liệu bản đồ thời tiết GeoJSON cho số lượng lớn người dùng cùng lúc (đặc biệt khi có bão đổ bộ), giảm thiểu tải truy vấn đọc lặp lại xuống PostgreSQL/PostGIS. Đồng thời, hệ thống cần kiểm soát tần suất chat AI (Rate Limiting) chính xác và giữ cho Backend Spring Boot hoàn toàn Stateless để sẵn sàng scale ngang.
- **Decision:**
  Triển khai **Redis 7.2 (Alpine)** làm bộ nhớ đệm phân tán tập trung (Distributed Cache) và lưu trữ Token Bucket của Bucket4j. Tích hợp thông qua `spring-boot-starter-data-redis` (Lettuce driver). Giới hạn bộ nhớ `maxmemory 128mb` với chính sách `allkeys-lru` để tối ưu chi phí RAM máy chủ.
- **Alternatives:**
  Caffeine (Local In-Memory Cache), Memcached, Hazelcast.
- **Consequences:**
  - _Tích cực:_ Phản hồi API thời tiết GeoJSON trong < 2ms; giảm 95% tải truy vấn xuống CSDL PostGIS; Backend hoàn toàn stateless, sẵn sàng scale ngang nhiều instance mà không lo phân mảnh cache; quản lý Rate Limit an toàn chống cạn kiệt ngân sách token Gemini API.
  - _Tiêu cực:_ Tốn thêm ~50MB RAM trên máy chủ VPS; phát sinh thêm 1 container trong Docker Compose; độ trễ mạng nội bộ TCP ~0.5ms so với truy xuất bộ nhớ heap trực tiếp.
- **Trade-offs:** Chấp nhận tốn thêm một lượng nhỏ RAM (~50MB) và 1 container dịch vụ để đạt được khả năng mở rộng (Scalability), tính nhất quán (Consistency) và độ phản hồi tức thì cho WebGIS client.

### ADR-006: Sử Dụng React 18 + Leaflet Với Định Dạng Chuẩn RFC 7946 GeoJSON

- **Status:** Accepted
- **Context:**
  Cần trực quan hóa bản đồ thời tiết Việt Nam với các lớp mưa, vector gió, xoáy bão và tích hợp mượt mà với khung chat AI trên cùng một màn hình web.
- **Decision:**
  Sử dụng thư viện **Leaflet 1.9.4** kết hợp **React 18** và **TypeScript**. Toàn bộ API Backend cung cấp dữ liệu không gian tuân thủ nghiêm ngặt chuẩn **RFC 7946 GeoJSON (WGS84 EPSG:4326)**.
- **Alternatives:**
  Mapbox GL JS, OpenLayers, Google Maps JavaScript API.
- **Consequences:**
  - _Tích cực:_ Dung lượng thư viện siêu nhẹ (~40KB gzip), tải trang cực nhanh; nạp trực tiếp GeoJSON từ Backend qua `L.geoJSON` mà không cần convert; miễn phí bản quyền; cộng đồng lớn.
  - _Tiêu cực:_ Không có hiệu ứng địa hình 3D xoay nghiêng (không cần thiết đối với yêu cầu dự án).
- **Trade-offs:** Chọn sự đơn giản, nhẹ nhàng và miễn phí thay vì đồ họa 3D nặng nề của Mapbox GL.

### ADR-007: Cơ Chế Dual-Layer AI Grounding Kết Hợp Deterministic Fallback Guardrails

- **Status:** Accepted
- **Context:**
  Cảnh báo thiên tai đòi hỏi độ chính xác tuyệt đối về số liệu đo đạc. AI hallucination (tự bịa số liệu) là rủi ro nghiêm trọng nhất có thể làm thất bại dự án. Đồng thời, dịch vụ bên thứ ba (Gemini API) có thể gặp sự cố gián đoạn mạng hoặc timeout.
- **Decision:**
  Áp dụng kiến trúc bảo vệ 3 lớp:
  1. _Lớp 1 (Factual Context Injection):_ Truy vấn số liệu thực tế từ PostGIS, tiêm nguyên bản vào System Prompt với Temperature thấp (0.2).
  2. _Lớp 2 (Output Guardrail Validator):_ Dùng Regex kiểm tra các con số trong văn bản do Gemini sinh ra có trùng khớp với số liệu đầu vào hay không.
  3. _Lớp 3 (Deterministic Fallback Template):_ Nếu Gemini timeout (> 5s), trả về lỗi HTTP 5xx, hoặc phát hiện ảo giác số liệu $\rightarrow$ Tự động chuyển sang điền số liệu vào mẫu câu định sẵn (`SR-AGT-003`).
- **Alternatives:**
  Sử dụng LLM độc lập không có đối soát, Fine-tuning mô hình riêng.
- **Consequences:**
  - _Tích cực:_ Bảo đảm 100% cảnh báo phát ra đều có số liệu trung thực; hệ thống không bao giờ bị tê liệt hay trễ giờ cảnh báo ngay cả khi Google Cloud gián đoạn.
  - _Tiêu cực:_ Cần viết thêm module kiểm tra regex và bảo trì tập mẫu câu dự phòng.
- **Trade-offs:** Tăng thêm một lượng nhỏ logic backend để đổi lấy độ an toàn tuyệt đối về mặt thông tin công cộng.

### ADR-008: Triển Khai Bằng Docker Compose Trên VPS Thay Vì Kubernetes Cho MVP

- **Status:** Accepted
- **Context:**
  Cần đưa hệ thống lên môi trường Production với chi phí tiết kiệm nhất, triển khai tự động qua CI/CD và quy trình vận hành đơn giản cho đội ngũ 1-2 kỹ sư.
- **Decision:**
  Đóng gói toàn bộ hệ thống (Nginx, Spring Boot Backend, PostGIS DB) thành các Docker container và điều phối bằng **Docker Compose** trên 1 máy chủ VPS (Ubuntu 22.04 LTS). **KHÔNG dùng Kubernetes**.
- **Alternatives:**
  Kubernetes (EKS/GKE/K3s), Serverless (AWS Lambda), Triển khai trực tiếp không container (Bare-metal installation).
- **Consequences:**
  - _Tích cực:_ Chi phí máy chủ chỉ từ $10 - $20/tháng; cấu hình toàn bộ hạ tầng gói gọn trong 1 file `docker-compose.yml`; phục hồi sau sự cố chỉ mất 30 giây; triển khai đồng nhất giữa Dev và Prod.
  - _Tiêu cực:_ Không có tính năng tự động co giãn từng pod độc lập (Auto-scaling pod) của Kubernetes.
- **Trade-offs:** Đánh đổi khả năng auto-scale phức tạp để lấy sự đơn giản, tiết kiệm chi phí và độ tin cậy tuyệt đối trong giai đoạn MVP.

### Why this stack fits the project

Ngăn xếp công nghệ trên được kết hợp chặt chẽ để tạo thành một thể thống nhất hoàn hảo cho dự án WebGIS Thời tiết Việt Nam vì các lý do:

1. **Đáp ứng 100% Yêu cầu Chức năng (Functional Alignment):**
   - Leaflet và PostGIS là cặp bài trùng hoàn hảo trong ngành GIS, xử lý mượt mà việc hiển thị 63 trạm đo và quỹ đạo bão theo chuẩn mở WGS84 GeoJSON.
   - Spring Boot và Java 21 cung cấp bộ khung vững chắc cho các tiến trình quét định kỳ, bảo vệ an toàn các endpoint quản trị và điều phối AI Agent.
   - Gemini 1.5 Flash mang lại khả năng sinh văn bản tiếng Việt tự nhiên, giải quyết triệt để bài toán chuyển hóa số liệu thô thành ngôn ngữ đại chúng.

2. **Hiệu Năng & Độ Tin Cậy Vượt Trội (Performance & Reliability):**
   - Nhờ chỉ mục không gian GiST của PostGIS và tầng đệm Redis Cache (TTL GeoJSON 15m), thời gian phản hồi của các API bản đồ luôn duy trì dưới 2ms.
   - Virtual Threads của Java 21 cho phép hệ thống gọi đồng thời hàng chục trạm đo OpenWeatherMap mà không bị nghẽn thread.
   - Cơ chế **Deterministic Fallback** bảo đảm cảnh báo luôn được phát ra đúng giờ kể cả khi dịch vụ AI bên ngoài gặp sự cố.

3. **Bảo Mật & Tính Riêng Tư (Security & Privacy):**
   - Tuân thủ tuyệt đối quy định không thu thập PII của người dân thông qua mô hình phiên ẩn danh.
   - Phân tách ranh giới rõ ràng: Khách vãng lai bị Rate Limit trên Redis bảo vệ tài nguyên; Quản trị viên và Worker được bảo vệ bằng mã khóa bí mật độc lập.

4. **Tối Ưu Hóa Chi Phí Tuyệt Đối (Cost Optimization):**
   - Không phát sinh chi phí bản quyền phần mềm (100% Open Source).
   - Không tốn chi phí duy trì cụm máy chủ đắt tiền (không Kafka, không Kubernetes, không cụm Redis phân tán phức tạp, không GPU server); Redis 7 Alpine nhẹ (~30-50MB RAM) chạy chung trên VPS.
   - Toàn bộ hệ thống chạy mượt mà trên **01 máy chủ VPS với chi phí chỉ $10 - $20/tháng**.

5. **Tiến Độ Phát Triển Nhanh Chóng (Development Timeline):**
   - Cấu trúc Modular Monolith và Monorepo giúp 1-2 kỹ sư full-stack có thể phát triển, kiểm thử và bàn giao sản phẩm MVP hoàn chỉnh trong vòng 4 đến 6 tuần mà không bị phân tán bởi các vấn đề hạ tầng phức tạp.

## 18. Technology Not Used

Phần này ghi nhận minh bạch các công nghệ phổ biến trên thị trường nhưng **cố tình không sử dụng** trong dự án, khẳng định quyết định kỹ thuật được đưa ra dựa trên phân tích yêu cầu thực tế chứ không chạy theo trào lưu:

```
┌────────────────────────────────────────────────────────┐
│             CÔNG NGHỆ CỐ TÌNH KHÔNG SỬ DỤNG            │
├──────────────────────────┬─────────────────────────────┤
│ ❌ Apache Kafka / RabbitMQ│ ❌ Kubernetes (K8s)          │
│ ❌ Memcached / Hazelcast │ ❌ MongoDB / NoSQL          │
│ ❌ Elasticsearch / VecDB │ ❌ Microservices Architecture│
│ ❌ gRPC                  │ ❌ AWS Lambda / Serverless   │
│ ❌ GraphQL               │ ❌ Mapbox GL JS (Commercial) │
└──────────────────────────┴─────────────────────────────┘
```

1. **Apache Kafka / RabbitMQ $\rightarrow$ NOT USED**
   - _Lý do:_ Nhu cầu nạp dữ liệu khí tượng có tính chất chu kỳ (Batch Polling mỗi 15-30 phút), không phải luồng sự kiện liên tục hàng triệu message/giây. Spring TaskScheduler (`@Scheduled`) in-process giải quyết trọn vẹn bài toán mà không tốn 2GB RAM cho cụm broker ngoài.

2. **Kubernetes (K8s) $\rightarrow$ NOT USED**
   - _Lý do:_ Hệ thống là Modular Monolith chỉ gồm các container thiết yếu (Nginx, Backend, PostGIS, Redis). Triển khai Kubernetes là biểu hiện kinh điển của over-engineering, làm tăng chi phí máy chủ lên gấp 5 lần và đòi hỏi kỹ năng vận hành phức tạp không cần thiết cho giai đoạn MVP.

3. **Redis Cluster Phân Tán Đa Cụm (Multi-Node Sentinel / Cluster) $\rightarrow$ NOT USED**
   - _Lý do:_ Hệ thống sử dụng 01 container Redis 7 Alpine độc lập gọn nhẹ (Single-instance) trong Docker Compose là đủ gánh tải toàn bộ nhu cầu cache và rate limit. Không cần thiết lập kiến trúc Redis Cluster đa node phân tán hay Sentinel phức tạp gây lãng phí tài nguyên và chi phí vận hành ở giai đoạn MVP.

4. **MongoDB / NoSQL $\rightarrow$ NOT USED**
   - _Lý do:_ Dữ liệu của hệ thống có tính toàn vẹn quan hệ chặt chẽ (Trạm đo, Bản ghi thời tiết chuỗi thời gian, Cơn bão, Quỹ đạo, Ngưỡng, Cảnh báo). MongoDB không có ràng buộc khóa ngoại cứng và năng lực tính toán không gian trắc địa cầu kém xa PostGIS.

5. **Elasticsearch / Dedicated Vector Database (Pinecone, Chroma, Milvus) $\rightarrow$ NOT USED**
   - _Lý do:_ Tính năng Grounding của AI Chatbot truy xuất dữ liệu dựa trên các thuộc tính cụ thể: thời gian mới nhất, trạm có lượng mưa cao nhất, khoảng cách bão gần nhất. Các phép toán này được xử lý tối ưu bằng SQL B-Tree và PostGIS GiST index. Hệ thống không cần tìm kiếm tương đồng vector (Semantic Search) trên hàng triệu văn bản phi cấu trúc.

6. **Microservices Architecture $\rightarrow$ NOT USED**
   - _Lý do:_ Chia nhỏ hệ thống thành 5-6 microservices độc lập (Location Service, Weather Service, Storm Service, Alert Service, Chat Service) ở giai đoạn này sẽ dẫn đến thảm họa phân tán: Network latency giữa các service, Distributed Transaction (Saga pattern), Service Discovery, API Gateway phức tạp. Kiến trúc **Modular Monolith** mang lại đầy đủ ranh giới module rõ ràng mà không phải chịu chi phí phân tán.

7. **gRPC $\rightarrow$ NOT USED**
   - _Lý do:_ Client chính của hệ thống là trình duyệt Web (React SPA). Trình duyệt không hỗ trợ trực tiếp chuẩn HTTP/2 gRPC nhị phân mà phải qua gRPC-Web proxy trung gian. Dữ liệu bản đồ GeoJSON RFC 7946 chuẩn RESTful là định dạng tương thích tự nhiên nhất với thư viện Leaflet.

8. **AWS Lambda / Serverless Architecture $\rightarrow$ NOT USED**
   - _Lý do:_ Các tiến trình ngầm giám sát ngưỡng và nạp dữ liệu cần chạy liên tục theo chu kỳ thời gian thực. Serverless có chi phí đắt đỏ khi chạy tác vụ định kỳ thường xuyên, gặp vấn đề Cold Start Latency khi người dùng truy cập web, và việc kết nối Lambda vào PostGIS đòi hỏi cấu hình RDS Proxy tốn kém.

9. **GraphQL $\rightarrow$ NOT USED**
   - _Lý do:_ Cấu trúc dữ liệu trao đổi của hệ thống rất cố định và rõ ràng theo chuẩn GeoJSON FeatureCollection. REST API với cấu trúc URL ngữ nghĩa `/weather/current`, `/storms/{id}/track` là tối ưu, dễ cấu hình HTTP caching tại tầng Nginx hơn rất nhiều so với GraphQL (vốn luôn gửi HTTP POST).
